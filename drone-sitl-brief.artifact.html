The systemOverview
What this is

A sandbox for a drone perception contest

The repo is a practice rig, not the contest itself. It stands up a full flight stack — autopilot, physics, photoreal camera, a web control panel — so control code and perception code can be flown and broken safely, long before they meet the real hardware.

The task

Fly a survey pattern, spot vehicles from the air, read the text on them. Scored on detection plus ATE — how tightly the aircraft tracks the planned path.

The real rig

A custom flight controller, not PX4. The competitor never touches attitude or motors — they get a thin control API and a camera feed.

This week

Two things landed: proportional stick control for the human pilot, and flight() — the competitor control primitive — implemented for real in the sandbox.

The systemComponents
The stack

Four processes, one aircraft

PX4 SITL

The autopilot, unmodified, running on the host. Estimator, controllers, MAVLink — exactly the firmware, just no board.

Isaac Sim

Rigid-body physics and the photoreal render. Owns the world and, crucially, owns time.

Cesium terrain

Real-world elevation and imagery tiles streamed in, so the camera sees actual ground, not a grey plane.

Web flight deck

A browser panel on :8090 — joystick, live telemetry, map, sim freeze, agent upload & run.

MAVLink carries commands and telemetry between PX4 and the bridge. A separate HIL channel carries motor thrusts out and sensor truth back between the bridge and Isaac. The web deck talks to the bridge over WebSocket.

The systemLockstep
The lockstep loop

The simulator is the clock master

  • Isaac advances one physics step, then pauses.
  • It sends PX4 a fresh sensor frame stamped with sim time — IMU, baro, the pose the estimator needs.
  • PX4 runs one controller iteration and replies with per-rotor thrust, 0–1. Nothing else — no attitude, no rates.
  • Isaac applies those thrusts, steps again. Repeat at the FC's native rate.
Why it matters Wall-clock and sim-clock drift apart the moment either side is busy. In lockstep the estimator never sees a jittered dt, so SITL behaves identically on a loaded box and an idle one — runs are reproducible.
The failure mode

Freeze the stream for more than ~30 s, or restart the tap mid-run, and PX4 wedges — it needs a full restart. Covered on the freeze-tap slide.

II

Pilot in the loop

Making the web deck fly like a real transmitter — and being able to stop the world and look at it.

Pilot in the loopControl input
Dual-stick joystick control

From buttons to deflection

Before

WASD and a d-pad. Each key a boolean held-set: pressed meant "full speed that way", released meant "stop". No in-between, so no gentle corrections — every input was a lurch.

After

Two on-screen sticks. Each axis is a continuous [−1, 1] deflection sent as a {type:"stick"} message. Half stick is half speed. --speed-right tunes the translation stick independently.

One change, touching every layer:

  • offboard — proportional setpoints replace the boolean held-set
  • joystick-server — handles {type:stick} over WebSocket, adds --speed-right
  • web/ and web-v2/ — the dual-stick widget replaces WASD / d-pad in both UIs
Pilot in the loopInput path
Stick → velocity

Where the numbers get flipped

  • The widget reports screen axes — y is DOM-down. The UI corrects that sign before anything else.
  • axes_to_body_velocity() scales each axis by its speed constant into a body-NED setpoint.
  • NED means +z is down, so "climb" is negative vz. The +up → NED flip lives in exactly one place: agent_control / CommandState.
  • Stop sending and the setpoint decays to hover after the watchdog window — a stuck stick is a hazard.
# offboard.axes_to_body_velocity
def axes_to_body_velocity(pitch, roll, thrust,
        speed_fwd, speed_right, speed_up):
    vx = pitch  * speed_fwd      # nose  +fwd
    vy = roll   * speed_right    # right +stbd
    vz = -thrust * speed_up      # NED: climb = -vz
    return vx, vy, vz            # body frame, +down

The same function serves the human stick and, later, flight().

Pilot in the loopHIL freeze tap
sim/hil_tap.py

Stop the world and look at it

  • The tap sits inline on the PX4↔Isaac HIL stream, forwarding every packet.
  • Hit FREEZE SIM on the page and it stops forwarding — both sides block, sim time stops, the frame is held still for inspection.
  • A live readout and /hil/status expose what's flowing.
Fixed along the way A 3 s socket-timeout crash, and a thaw deadlock on unfreeze. Static JS got a no-cache header after a stale browser cache silently broke the button with zero errors in the console.
Hard limit

Freeze longer than ~30 s, or restart the tap while PX4 is up, and PX4 wedges. Lockstep has no notion of a 30 second gap. Recovery is a full restart — the freeze is a microscope, not a pause button for a coffee break.

III

flight() — the one primitive

The whole competitor-facing control surface, and how a single call travels from their code to a PX4 setpoint.

flight()Context
The competition, briefly

Perception, not airmanship

The founding premise: teams are scored on what they see and read, not on how well they fly. That shapes every API decision below.

Detection score

Find the vehicles, read the text, submit an answer. The real contest.

ATE score

Absolute trajectory error against the planned survey track. Leave the track and ATE pauses; the detection-scoring window opens.

Deployment

The competitor's script runs as a local subprocess on the organiser's box, against the local FC. No Jetson, no network hop.

Unresolved tension An ATE score is scoring airmanship — it collides with the premise. Held open deliberately; see the Route slide.
flight()Submission shape
Shape of a submission

You do not write the loop

class MyAgent(Agent):

    def on_start(self, arena): ...   # once, models

    def on_frame(self, image, state):
        # ~5 Hz  — heavy perception

    def on_tick(self, state):
        # ~20 Hz — cheap steering, no image

    def on_arrival(self, state): ...
    def on_waypoint(self, i, state): ...
    def on_route_complete(self, state): ...
  • The harness owns the loop and calls your methods at fixed rates.
  • Each callback returns a Command — a flight command, a camera switch, or both.
  • Return None and the aircraft keeps doing what it was doing. A slow detector never stalls the aircraft.
  • Events (on_arrival, on_waypoint…) are synthesised from mission telemetry, not polled.
flight()Timing contract
Callbacks & budgets

The sim does not wait for you

CallbackRateBudgetIf you overrun
on_frame~5 Hz200 ms call abandoned on a worker thread — previous command holds
on_tick~20 Hz50 ms call abandoned — previous command holds
eventsas they occur200 ms call abandoned
The rule A callback that overruns is joined with a timeout and dropped. A genuinely wedged one leaves a parked daemon thread; killing the process is the backstop.
Why real-time, not stepped

The simulation runs in wall time. A slow script is a drone that flew blind while you were thinking — penalised by physics, not by a rule.

flight()Signature
The one primitive

flight(left_x, left_y, right_x, right_y)

from competition import Agent, Command, flight

return Command(flight=flight(0, 0, 0, 1.0))   # full speed straight ahead
return Command(flight=flight(0, 0, 0.4, 0.8)) # forward + a little strafe right
return Command(flight=flight(0.6, 0, 0, 0))   # spin right in place

Two sticks

Left stick and right stick, like a real transmitter. Four axes total.

Normalised

Every axis is a continuous [−1, 1]. Full deflection on a translation axis = 5 m/s. Yaw full = 45°/s.

A frozen dataclass

Validated to range on construction. An out-of-range axis is a ValueError at the call site, not a silent clamp in flight.

flight()Axis map
The four axes

State the deflection you want

StickAxisControls+1 means
leftleft_ythrustfull climb
leftleft_xyawfull right / clockwise
rightright_ypitchfull forward
rightright_xrollfull right / strafe
Not buttons There are no discrete direction commands. "You have no fingers" — you state a vector, the aircraft holds that deflection.
Positive-up thrust left_y = +1 climbs. This is not NED — the one sign flip that trips people up. The conversion to +down happens server-side, once.
flight()Design · form
Cartesian, not polar

No angle, no magnitude

Rejected

flight(bearing_deg, push) — an angle 0–360 plus a push amount. Reads nicely in prose.

But a script never has an angle. It has a direction vector — from a detection, a bearing calc, a difference of positions.

Chosen

Four Cartesian axes. The vector goes straight in. No atan2 to enter polar, no sin/cos to leave it.

The validation spike wrote the polar version first — it was pure overhead, rewritten to Cartesian with zero round-trip.

Same shape the human joystick UI already produces internally — (pitch, roll, yaw, thrust). flight() hands it over directly.

flight()Design · frame
Body frame, not world frame

Nose-relative, always

  • right_y = +1 is "forward from the nose", not "north". There is no VelocityWorld counterpart any more.
  • Steering toward a lat/lon target means rotating the world bearing into the body frame yourself.
  • Judged ~4 lines — not worth a world_to_body() helper, unlike the genuinely hard pixel_to_ground() camera math.
  • state.lat / lon / heading arrive with every callback — no polling call needed.
# world bearing (north, east)  ->  flight() body axes
h  = math.radians(state.heading)
rx = north * math.sin(h) + east * math.cos(h)
ry = north * math.cos(h) - east * math.sin(h)
return Command(flight=flight(0, 0, rx, ry))

Detections come back in map coordinates, so this is the only coordinate translation a competitor ever writes.

flight()Design · lifetime
Stateless & watchdogged

Re-issue it, or it decays

  • flight() carries no state. It is a setpoint for now, not a command that latches.
  • No new flight() within ~0.5 s and the server watchdog decays it to a hover.
  • To hold a heading, return the same flight() every on_tick. To hold position deliberately, return flight(0,0,0,0) every tick.
  • A silent script must not leave a velocity running — a stuck setpoint is the same hazard as a stuck stick.
Same shape as the old Velocity Velocity was already stateless and watchdogged. flight() keeps that contract exactly — only the axis layout changed, not the lifetime model. Nothing to unlearn.
Common mistake

Expecting flight() to persist. It won't. Use Route or Inspect for anything you want the server to hold.

flight()Reuse
One conversion, two callers

flight() is the joystick, in code

The human stick and flight() converge on the same function. set_flight() is a thin adapter — a coordinate-shape change, no new control logic.

Added

AgentControl.set_flight() — reuses offboard.axes_to_body_velocity and axes_to_yaw_rate, the exact calls CommandState makes for the web UI.

Deleted as now-dead code

set_velocity_world, offboard.send_velocity_world, MAV_FRAME_LOCAL_NED — the world-frame path had no caller once VelocityWorld was gone.

Payoff The competitor's straight-line flight and the pilot's stick input are now the same code path — one place to tune, one place for a bug to hide.
flight()Boundaries
What flight() deliberately can't do

flight() is the floor

Not availableWhy
Attitude / rate / motor control the stabilisation loop can't cross a process boundary — a hiccup puts it in the ground
Acceleration setpoints a stale acceleration diverges quadratically, not linearly
Blocking calls (goto_and_wait) the harness owns the loop; a blocking call stalls your own tick. Completion arrives as an event
Gimbal / zoom cameras are rigidly bolted on — you aim by flying, magnify by switching lens
Discrete direction commands state the deflection you want; there is no "nudge left"

Everything removed is either a safety hazard across a boundary or trivially rebuildable on flight() itself.

flight()Route & Inspect
The two that stayed

Route & Inspect — and one open question

Route

Interpolates the whole polyline on the sim host at the FC's native rate (250 Hz–1 kHz). A hand-rolled flight() sweep only updates at on_tick — visibly choppier over a 24-minute survey. Its pause/resume state also is the on-track / off-track signal for scoring.

Inspect

Solves the standoff triangle — distance, altitude, heading — so the oblique camera ends up looking at the point you named. Inherently an off-track manoeuvre, so it never competes with ATE.

Open: Route vs ATE Route flies identically well for every team regardless of their code. If it's usable during the ATE-scored track, ATE stops differentiating anyone. Leading candidate: cut Route, fly the track by hand with flight(), switch the ATE trigger to a geofence check. Not yet grilled — the sandbox ships Route as-is until it is.
flight()Validation
Proven before it was written up

A 15-line guidance loop flew it

The test

Throwaway spike against live Isaac Sim + PX4 SITL. A proportional bearing/distance loop on flight(), decelerating on approach.

Result

Target 47 m offset (40 N, 25 E). Arrived within 2 m, altitude held within 0.1 m, zero yaw — a world target needs only the body rotation, no heading change.

Bug caught

Draining one MAVLink message per tick starves position updates under load. Fix: drain all pending messages per tick, like the joystick server already does.

Conclusion: flight() alone is a sufficient floor primitive. Route's smoothness claim is argued structurally, not yet measured.
